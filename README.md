# The Keeper's Domain

Mobile dig-and-build dungeon management prototype — original IP, inspired by (but not derived from) Dungeon Keeper. See [Docs/project-brief.md](Docs/project-brief.md) for the full brief.

The digging creature is called an **Impling** — small for now (1/3 tile size), up to two can work the same tile at once. The idea of implings growing into a full-size Imp after enough digging is noted for later but not implemented yet.

Digging is HP-based, not a flat timer: each Rock tile has 100 HP (200 if reinforced, see below), and an impling deals 20 HP per hit on a 1-second cadence, checking after every hit whether the tile has broken through. Two implings sharing a tile roughly double the break speed since their hits stack against the same HP pool. Tile color darkens as it takes damage, independent of the queued/claimed/reinforced tint.

Everything is built from placeholder primitives (cubes/capsules) and spawns procedurally at runtime via [`GameBootstrap`](Assets/Scripts/Core/GameBootstrap.cs) — the `Prototype.unity` scene itself is empty, so there's nothing to hand-wire in the Inspector.

The starting layout is two fixed rooms joined by a single one-tile corridor, all pre-carved as Floor+Claimed by `GameBootstrap` (`DungeonGrid.CarveRoom` always claims what it carves) — a 5x5 **Chaos Core** room at the grid center, and a 3x3 **Portal room** to its east, both claimed by default from the moment the game starts. [`Portal.cs`](Assets/Scripts/Rooms/Portal.cs) builds a small 3-step staircase visual on its room's center tile out of cube primitives, standing in for the way up to the overworld — it no longer does any territory claiming itself (see below). [`ChaosCore.cs`](Assets/Scripts/Rooms/ChaosCore.cs) is this project's original-IP stand-in for the genre's usual "heart" room — for now just a placeholder structure on the center 3x3 of its room: a raised platform (same height as the portal's *second* staircase step) with a color orb on top standing in for the player's color, until an actual player-color system exists.

The game starts with **4 implings** already spawned, one on each corner of the Chaos Core's 3x3 platform (`GameBootstrap.SpawnStartingImplings`, using `ChaosCore.PlatformHalfSize` rather than a duplicated magic number) — those corner tiles are still plain walkable Floor underneath the platform's visual overlay, so this goes through the exact same `ImplingSpawner.SpawnImplingAt` mana-summon the Impling menu's button uses. Implings are mana-conjured creatures, not Lair-dependent, so no Lair is required — each of the 4 reserves its upkeep mana from the Chaos Core exactly like any other spawn.

Beyond those two starting rooms, territory is claimed entirely by a second impling task, not by proximity to the portal. `DungeonGrid.CompleteDig` no longer auto-claims a newly-dug tile — it fires `FloorNeedsClaim` instead, and `BuilderJobBoard` queues that coord as a **claim job**: single-worker, no grace period (nothing for the player to mis-tap, since it's automatic), and resolved once an impling stands on it for `ImplingAgent._claimDuration` seconds and calls `BuilderJobBoard.ApplyClaim`. This means freshly dug floor sits Unclaimed (and un-Lair-able, since `LairManager.CanPlaceFootprint` requires `Ownership == Claimed`) until an impling gets around to claiming it. A claim job also isn't offered to anyone until it borders at least one already-Claimed tile (`DungeonGrid.BordersClaimedTile`) — territory has to grow outward from the claimed frontier one ring at a time, rather than an impling being free to claim any reachable dug-out tile regardless of how disconnected it is from the domain so far.

A third impling task, **reinforcing**, lets the player thicken a wall before it's dug: tapping a Rock tile while the Build menu's Build mode radio is set to Reinforce mode (see Controls) queues a `RequestReinforce` job with the same 1-second mis-tap grace period digging uses. An impling that finishes one calls `BuilderJobBoard.ApplyReinforce` → `DungeonGrid.CompleteReinforce`, which sets `TileState.IsReinforced`, tops the tile's HP up to `TileState.ReinforcedMaxHp` (200, vs. the normal 100), and darkens its color. A reinforced wall is still just Rock underneath — digging it back out works exactly as before, it just takes twice the hits. Queuing for dig and queuing for reinforce are mutually exclusive on a given tile (`DungeonGrid.RequestDig`/`RequestReinforce` each reject if the other is already queued), and there's no repair mechanic yet, so an already-reinforced tile can't be queued again.

A fourth impling task, **building**, is the reverse of digging: tapping a Claimed, room-free Floor tile while Build mode is set to Construct wall (see Controls) queues a `RequestBuild` job, same 1-second grace period. An impling that finishes one calls `BuilderJobBoard.ApplyBuild` → `DungeonGrid.CompleteBuild`, turning the tile back into ordinary full-HP Rock — Ownership is left untouched (still Claimed), so digging it back out later doesn't need a fresh claim job. Queuing for build requires the tile already be Claimed and room-free, which is enough on its own to keep it mutually exclusive with a pending claim job (an Unclaimed tile always fails the build gate) without needing a separate check.

Dig, claim, reinforce, and build jobs are all ranked the same way (nearest-by-travel-distance, see below) but as four separate pools, each with its own candidate-gathering and validity rules: `BuilderJobBoard.TryClaimNearestJob` walks `_jobPriorityOrder` (`Dig`, `Reinforce`, `Build`, `Claim` by default) and fully depletes whichever kind comes first in that list before even looking at the next one. The bottom menu bar's Impling menu has an up/down-reorderable list wired straight to `BuilderJobBoard.SetJobPriorityOrder`, seeded from `GetJobPriorityOrder` so the UI never has to guess the board's actual current order. Digging specifically can also be paused outright (`BuilderJobBoard.SetDigJobsPaused`, the Build menu's "Pause dig queue" toggle) — implings already mid-dig keep going, but no new dig job gets assigned while paused, so idle implings fall through to Reinforce/Build/Claim instead.

### Resources: gold, mana crystals, and the impling economy
Some Rock tiles are resource veins instead of plain wall (`TileState.WallResourceType`), scattered at level-gen by `GameBootstrap.ScatterResourceWalls` (a fixed-seed pass over every still-Rock tile once all the starting rooms are carved, so it can't land on them) — low, independent odds per tile of becoming one of:
- **Gold Wall** — 200 HP, gold-tinted with a handful of randomly-scattered gold-nugget decoration cubes (`DungeonGrid.RebuildWallDecoration`, seeded per-tile so the pattern is stable rather than re-randomizing every hit).
- **Regenerating Gold Wall** — 1000 HP, regenerates 15 HP after any hit that doesn't finish it off, more/brighter nuggets than a plain Gold Wall ("switch the amount of gold & rock"). At the default 20 HP/hit this nets only 5 HP of real progress per hit — slow, but not literally infinite, since regen only fires on a hit that leaves the wall standing (`DungeonGrid.ApplyDigDamage`).
- **Mana Crystal Wall** — 100 HP, blue-teal colored, no decoration (the brief only asked for a color change on this one).

Every resource wall is mined, not dug: it's queued and assigned exactly like a plain Rock tile (same Mine-mode gesture, same `BuilderJobBoard` Dig job pool, same multi-worker sharing) — the only difference is what happens once an impling starts working it. `ImplingAgent.StartJobAction` checks the target tile's `WallResourceType` and enters `Mining` instead of `Digging`; each hit's yield (`DungeonGrid.ApplyDigDamage`'s `resourceType`/`resourceAmount` out params, `TileState.ResourceDropPerHp` = 1 gold/crystal per HP actually removed) goes straight into the impling's `ImplingInventory` rather than just breaking the wall for its own sake. This is a deliberate simplification over giving mining its own `JobKind`: reusing the Dig pool means it can't be prioritized independently of plain digging in the Impling menu's priority list, but a fifth full job-kind pipeline (pending/open/assigned pools, a `TryClaimMineJob`, etc.) felt like a lot of duplicate plumbing for what's otherwise identical queue/assignment behavior — worth revisiting if independent prioritization turns out to matter.

Each impling can carry up to `ImplingInventory.MaxWeight` (60) — gold and mana crystals both weigh 1 per unit. `TickMining` credits every hit's yield and, the moment the inventory hits capacity, abandons the job (`BuilderJobBoard.ReleaseJob`, so someone else — or the same impling later — can pick it back up) and heads off to deposit. `ImplingAgent.TrySeekJob` checks for a deposit before searching for a new job (full inventory) and again as a fallback if no job was found but there's still cargo left (e.g. a partial load after some other interruption), so an impling only ever returns to the Lair empty-handed. Gold goes to the nearest **Treasury** tile with room (`TreasuryManager.TryFindNearestTileWithRoom`, same reachable-distance flood-fill as job ranking); mana crystals go to the Chaos Core, which has no capacity limit. Both deposit targets are themselves walkable Floor tiles, so the impling paths directly onto them rather than needing an adjacent approach tile the way a Rock-tile job does.

The **Treasury** is a player-buildable room, placed exactly like a Lair (see Controls/Bottom menu bar below) — `TreasuryManager.TryPlaceTreasury` drags out a rectangle with the same live valid/invalid ghost preview and the same underlying validity rule Lair placement uses (`DungeonGrid.CanBuildRoomOn`: Claimed, dug, room-free, buildable Floor), and it's sellable through the same generic Sell tool a Lair uses — `TreasuryManager` just listens for `LairManager.RoomSold` and cleans up its own gold/visual bookkeeping for whichever room (by id) got sold, rather than the Sell tool needing to know Treasury exists at all. The game starts with one already placed north of Chaos Core, off its own single-tile corridor, exactly as if the player had built it themselves — not a fixed landmark. Each tile stores up to 500 gold independently and shows the current amount as a small flat number label sitting on the tile's own gray-fill/gold-border surface.

Mana crystals deposited at the **Chaos Core** raise its **Max Mana** stat 1-for-1 (`ChaosCore.DepositManaCrystals`, `MaxManaPerCrystal` — the only ratio the brief pinned down was the crystal's own weight, so this conversion is a placeholder until a real mana economy exists) and a `TextMesh` label above the platform shows the current total.

Tiles have an `IsBuildable` flag (`TileState.IsBuildable`, queried via `DungeonGrid.IsBuildable`), mirroring `IsWalkable` — deliberately separate from `RoomId`/`HasRoom`, which drives the shared purple Lair-room tile color. Normal dug-out floor defaults to buildable (`DungeonGrid.CompleteDig`); `GameBootstrap` carves only the footprint that actually has a fixed structure on it — Chaos Core's center 3x3 platform, the Portal's single staircase tile, and the corridor tile — back to unbuildable, so a Lair can never overlap one of them without forcing them to render as if they were a Lair. The walkable margin around each room is left buildable, since it's the only claimed floor that exists before anything's been dug — without it there'd be no tile to ever place a first Lair on, and so no way to get a first impling at all. `LairManager.CanPlaceFootprint` checks the flag alongside the existing Type/Ownership/HasRoom checks.

### Controls
Every plain tap/drag on the grid is governed by the Build menu's **Build mode** radio (`TileInteractionController.BuildMode`, defaults to Mine mode):
- **Mine mode** — click/tap a Rock tile to queue it for digging; click/tap an already-queued one to un-queue it. Dragging across Rock tiles queues (or un-queues) every tile the drag passes over.
- **Reinforce mode** — same queue/un-queue gesture as Mine mode, but on `RequestReinforce` instead of `RequestDig`.
- **Construct wall** — same queue/un-queue gesture, but targets Claimed, room-free Floor tiles and queues/cancels a `RequestBuild` job.
- **View mode** — taps never queue anything. Tap a creature or a tile to inspect it: an impling's id/state/position, or a tile's type, HP (if a wall), ownership, room, and any pending queue — shown in the Build menu while it's open. This is the safe mode for just looking around without risking an accidental queue.
- **Hold Shift while dragging** (in Mine/Reinforce/Construct) — fills the whole rectangle between the drag's start and current point instead of just the tiles passed over, unless the Build menu's "Square mode" toggle is already on (Shift and the toggle both drive the same flag — see `TileInteractionController.SetSquareModeToggle`).
- **Bottom menu bar tools** (Lair, Treasury, Sell, Spawn Impling) — click the button, then act on the grid to execute it; see below. Placing a room is *only* reachable this way now — there's no more implicit "tap any Floor tile" fallback, since a plain Floor tap now means whatever the active Build mode says (or nothing, in View mode). Lair, Treasury, and Sell are all drags, not just taps: Lair/Treasury size the footprint to whatever rectangle you drag out, and Sell sells every room tile the drag passes over, whichever kind of room it is (a tap with no movement still works for the common single-tile case, for all three).
- **Touch**: two-finger drag to pan, pinch to zoom
- **Editor/mouse fallback**: right-drag to pan, scroll wheel to zoom

### Bottom menu bar
A permanent, always-visible bar ([`BottomMenuBar.cs`](Assets/Scripts/UI/BottomMenuBar.cs)) with four tab buttons, each opening a panel just above the bar (only one open at a time; clicking the open tab again closes it). Unlike the F1/F2 debug panels, this is meant to be the real game UI, but it only ever reads state through the same public APIs those panels use and forwards button presses — no duplicated game logic.
- **Build menu** — Square mode toggle; the **Build mode** radio (View/Mine/Reinforce/Construct wall, see Controls) with the inspected-tile/creature description shown underneath while View mode is active; **Pause dig queue** toggle (`BuilderJobBoard.SetDigJobsPaused`); a **Buildings** row with **Lair** (arms `PlacementAction.PlaceLair`, drags out a footprint), **Treasury** (arms `PlacementAction.PlaceTreasury`, same shape — `TreasuryManager.TryPlaceTreasury`), and **Sell** (arms `PlacementAction.SellLair` — see below for why this one's different, and why its name didn't need to change even though it now sells any room kind). While Sell is armed, a red "$" (`LairManager.ShowSellPreview`) floats above whatever room tile the pointer is currently over, live, even before a drag starts — a preview of what's about to be sold, not just feedback during the gesture itself.
- **Impling menu** — **Spawn Impling** (arms `PlacementAction.SpawnImpling`: next tap on a walkable tile calls `ImplingSpawner.SpawnImplingAt`, which summons an impling directly out of mana — the real spawning mechanic, not a debug shortcut; implings are mana-conjured creatures and don't need a Lair to exist, so the impling's "home" just becomes wherever it was summoned); an **Auto-reinforce dungeon walls** toggle, default off (`BuilderJobBoard.SetAutoReinforceEnabled` — see architecture notes for how it queues jobs itself instead of requiring a manual tap per wall); and the job-priority list described above.
- **Creatures menu** — the same id/state/position list as the F2 debug panel, just always reachable instead of F2-gated.
- **Tasks menu** — the same dig/reinforce/build/claim job lists as the F1 debug panel (cancel buttons where applicable), just always reachable instead of F1-gated.

The bottom bar's placement tools (`PlacementAction` in `TileInteractionController`) share one mechanism: arming a tool takes priority over Build mode entirely for the next gesture. Spawn Impling clears itself back to `None` right after firing, a single tap only. Lair, Treasury, and Sell are all drags instead: Lair and Treasury each drag out a footprint rectangle (with a live green/red valid/invalid ghost preview — `LairManager.UpdatePlacementPreview`/`TreasuryManager.UpdatePlacementPreview`, two independent copies of the same idea rather than one shared system, since each room type owns its own placement/validity/visual logic) and commit on release; Sell sells every room tile the drag passes over as it goes — the same line/square-paint mechanic Mine/Reinforce/Construct queuing already uses (`GestureMode.Sell` in `ApplyGestureAction`), just wired to `LairManager.TrySellRoom` instead of a grid queue call. `TrySellRoom` doesn't care what kind of room it's selling — it just clears the tile's `RoomId` and fires `RoomSold`, which `TreasuryManager` listens for to clean up its own gold/visual bookkeeping when a Treasury (rather than a Lair) gets sold this way; nothing needed to change in the Sell tool itself to make Treasury sellable. **Sell is also the one tool that doesn't clear itself after use**: it stays armed so the player can sell several rooms across separate gestures without re-pressing the button — the Sell button itself toggles it off (shown as "Sell (active)" while armed) rather than just re-arming an already-armed tool. A banner above the bar shows whichever tool is currently armed with a Cancel button (or, while a Lair/Treasury drag is actually in progress, the footprint size so far instead), since once its menu closes there'd otherwise be no visible sign a gesture is about to do something unusual.

### Debug tools
- **F1** — job board: dig, reinforce, and build jobs (each tracked tile with its status pending/open/active/unreachable, and a Cancel button only enabled where a tap-cancel would also work), plus a read-only claim-jobs list (open/claiming) below them. Also reachable in-game via the bottom menu bar's Tasks menu. [`DebugJobPanel.cs`](Assets/Scripts/Debug/DebugJobPanel.cs)
- **F2** — impling list: every spawned impling's id, current state, and grid position. Read-only, just for watching what each one is doing. [`ImplingDebugPanel.cs`](Assets/Scripts/Debug/ImplingDebugPanel.cs)
- **`Logs/gameplay-debug.log`** — timestamped event log, written automatically every Play session (fresh file each time, no setup needed): tile queued/promoted/canceled/destroyed, job claimed (by whom, travel distance, which side), and every impling state transition (`SeekingJob -> MovingToJob`, etc.) with its grid position at that instant. [`GameplayLog.cs`](Assets/Scripts/Debug/GameplayLog.cs). Timestamps are `Time.time` (seconds since Play started), which is what actually matters for ordering events against each other. Intended for exactly the kind of timing-sensitive bug this project has hit a few times already (job-promotion races, state-transition ordering) — paste the relevant slice of it back when reporting a bug like that instead of describing what you saw, since the log has the frame-by-frame order that's easy to miss by eye.

## Opening the project

This was scaffolded without a local Unity install, so there's no Editor here to generate the usual project files. To open it:

1. Install **Unity Hub** and a **Unity 6 LTS** editor release (`6000.0.x` or later — Personal license is fine, matches the brief's constraint).
2. In Unity Hub, choose **Open** → select this folder. `ProjectSettings/ProjectVersion.txt` pins `6000.0.36f1`, a placeholder version I couldn't verify against the actual latest patch (no internet access from here) — if your installed version differs, Unity will offer to auto-upgrade the project on open, which is safe to accept.
3. On first open, Unity will generate the rest of `ProjectSettings/` and `Packages/manifest.json` with defaults — no manual steps needed there.
4. Open `Assets/Scenes/Prototype.unity` and press **Play**. Switch the Game view to a portrait/landscape aspect and use **Device Simulator** (Window → Device Simulator) to test touch input without a physical device.

## Architecture notes

- `Grid`, `Implings`, `Rooms`, and `Camera` are kept decoupled per the brief: implings only ever talk to `BuilderJobBoard` (never `DungeonGrid` directly), and `LairManager` only announces `RoomPlaced` — it has no idea `ImplingSpawner` exists. This is meant to let combat/economy plug in later without rewrites. `BuilderJobBoard` is named generically (not `DigJobBoard`) since it's expected to grow more job types and to sit alongside other job boards later.
- Movement uses real A* pathfinding ([`AStarPathfinder.cs`](Assets/Scripts/Grid/AStarPathfinder.cs), 4-directional, uniform cost, linear-scan open set — plenty fast at this grid size) — implings walk an actual route over dug tiles rather than a straight line, so they no longer cut through undug rock. `ImplingAgent` plans a path once per trip (claiming a job, or heading back to the Lair) rather than every frame, since tiles only ever go Rock → Floor and never back, so a route found once stays valid for the whole walk.
- Job assignment favors the nearest idle impling by actual walking distance, not straight-line distance and not whichever impling happens to ask first. `DungeonGrid.GetReachableFloorDistances` flood-fills the connected walkable region from a position and records each tile's step count along the way — the reachability check and the distance ranking are the same pass, free of extra cost. `BuilderJobBoard.TryClaimNearestJob` runs this once for the requesting impling and once per other currently-idle impling (`BuilderJobBoard.SetWorkerAvailable` tracks who's idle, via the minimal `IJobWorker` interface so the board still doesn't depend on `ImplingAgent`), then skips a candidate job for the requester once enough *closer-by-travel-distance* idle workers exist to fill every remaining slot on that job first — counting against remaining capacity, not a flat "any closer worker blocks it," since a job can hold 2 workers and both should get to join if there's room. A queued tile with no dug path to it at all is skipped and tinted blue-gray as "unreachable" until digging elsewhere connects to it. Cost is roughly one flood-fill per idle impling per idle impling's turn (fine for a handful of implings on a grid tens of tiles across; would need caching or a cheaper heuristic if either grows a lot).
- Two implings sharing a dig job each run their own independent hit timer, and only the one whose hit actually breaks the tile finds out synchronously (`BuilderJobBoard.ApplyHit`'s return value). Originally the *other* worker had no way to learn its job was already done until its own next hit tick — up to a full `_hitInterval` (1s) of sitting there still marked `Digging` and still excluded from "nearest idle impling" job assignment, even though there was nothing left to dig. Fixed by having `ImplingAgent.TickDigging` check every frame (via `BuilderJobBoard.IsStillDiggable`) whether its job tile is still Rock at all, independent of its own hit cadence — a shared job finishing under it is now noticed next frame, not next hit.
- That fix above surfaced a second, separate bug: both implings sharing a tile would sometimes head back to the Lair together immediately after, even with other reachable jobs still queued and visibly available. First fix attempt (still valid, but not the actual cause caught in the log — see below): a freshly-queued tile sits in `_pendingJobs` for a 1-second grace period before `BuilderJobBoard.Update()` promotes it into `_openJobs`; since `BuilderJobBoard` and `ImplingAgent` are separate components with no guaranteed `Update()` order, a job search could in principle run before that frame's promotion had happened. Made promotion (`PromoteReadyPendingJobs`) also run synchronously at the start of `TryClaimNearestJob`, not only on the board's own per-frame tick, so a search always sees current results regardless of call order — a real improvement, but [`Logs/gameplay-debug.log`](Assets/Scripts/Debug/GameplayLog.cs) from an actual repro showed the real cause was something else entirely: `SetWorkerAvailable(this, true)` was only ever called from inside `TrySeekJob()`, i.e. on an impling's *own* next `Update()`. Two implings sharing a tile transition `Digging -> SeekingJob` mid-frame (inside `TickDigging`), which doesn't call `TrySeekJob()` — that's next frame. For the rest of that frame they're invisible to `HasEnoughCloserWorkersToFillSlots`'s "is someone closer" check, so implings already idling in the Lair (much farther away) would see zero competition, grab the newly-reachable job that frame, and leave the two implings standing right next to it with nothing — a textbook example of state and availability drifting out of sync by exactly one frame. Fixed by moving `SetWorkerAvailable` into `ImplingAgent.SetState` itself, so it fires the instant a state transition happens rather than waiting for that impling's own next `Update()`.
- `TileInteractionController` decides a gesture's action (queue vs. un-queue vs. place-room) once, from the tile under the very first frame of the press, and never re-evaluates it on release. Earlier this was two separate code paths — a drag handler that always queued, and a release-time tap handler that queued-if-unqueued/canceled-if-queued — which meant any tap lasting more than one frame (i.e. basically all real taps) got queued by the drag handler first and then immediately canceled by the tap handler, since by release time the tile already looked queued. Fixed by treating a tap as just a drag that never moved, sharing the same code path.
- `BuilderJobBoard` grew its second job type (claim, alongside dig) by giving each kind its own candidate pool and ranking method (`TryClaimDigJob`/`TryClaimClaimJob`) behind a shared dispatcher (`TryClaimNearestJob`) that tries the prioritized kind first and only falls back to the other if it's empty. Both methods reuse the same travel-distance ranking and closer-worker-fairness logic (`TryGetTravelDistanceToJob`, `HasEnoughCloserWorkersToFillSlots`) that dig jobs already had — claim jobs just plug in `remainingSlots: 1` since only one worker can ever claim a given tile. This removed the portal's old influence-radius auto-claiming (`TerritoryService`, deleted) entirely: the Chaos Core and Portal rooms are claimed only because `GameBootstrap` carves them pre-claimed, and everything else is claimed by an impling actually walking to it and finishing a claim job.
- A third job type, reinforce, followed the same shape again — `TryClaimReinforceJob` reuses the exact same ranking helpers as the other two — which is what motivated turning the priority setting from a single `_prioritizeDigging` bool into a `JobKind[] _jobPriorityOrder` array (`TryClaimNearestJob` just walks it and asks `TryClaimFromKind` for each in turn): a bool only ever expresses "which of two things comes first," and adding a third kind meant it had to become an actual order either now or on the very next job type, so it happened now while there were only three call sites to update.
- A fourth job type, build, is the mirror image of dig (Floor → Rock instead of Rock → Floor) but reuses the exact same single-worker, grace-period-then-cancelable, nearest-by-travel-distance shape reinforce already established (`TryClaimBuildJob`) — by this point adding a job kind is: one `TileState` flag, one pair of grid events + Request/Cancel/Complete methods, one pending/open/assigned trio of collections on the board, one `TryClaimXJob` method copy-adjusted from the nearest sibling, and one `ImplingState` + Start/Tick pair on the agent. `IsStillConstructable` is named to not collide with `DungeonGrid.IsBuildable`, which means something different (Lair-placement eligibility) despite the similar name.
- `BottomMenuBar` is deliberately a pure view over existing public APIs — it holds only UI-local state (which tab is open, mirrored toggle bools for square/pause, the reorderable priority list) and never touches grid or job-board internals directly. The placement-tool buttons (Lair, Treasury, Sell, Spawn Impling) all funnel through `TileInteractionController.RequestPlacement`/`PlacementAction` rather than the menu bar executing them itself, so there's exactly one place ("is a tool armed, and what happens on the next tap") instead of the menu bar and the tile-interaction code each tracking their own notion of it. `PointerOverPanel` (same pattern as the F1/F2 debug panels) stops a tap on the bar or an open panel from also landing on the world underneath.
- Mine/Reinforce/Construct started out as three different ways of picking a job kind for a plain tap — a straight tap for dig, holding Ctrl for reinforce, and a separate one-shot "Build Wall" placement button for build — which didn't scale (three inconsistent mechanisms for what's conceptually the same choice) and meant there was no way to just look around without risking a queue. Replaced with a single `BuildMode` enum (`View`, `Mine`, `Reinforce`, `Construct`) selected via a Build-menu radio group and read once at the start of each gesture (`TryGetModeTarget`) — the queue/un-queue/paint mechanics underneath are unchanged, only how the target job kind and tile-type get picked. `View` mode reuses the same tap-only gesture shape the old implicit Lair-placement fallback used (`_isViewTap`, resolved on release), but calls `Inspect` instead — a lookup of implings at that coord first, tile info otherwise, shown in the Build menu via `InspectedDescription`. Placing a Lair no longer has an implicit "any Floor tap" fallback, since a plain Floor tap now always means whatever the active BuildMode says; the explicit Lair placement-tool button is the only way to place one.
- `PlacementAction.SellLair` is the only placement tool that doesn't clear itself back to `None` after firing (`TryExecutePendingPlacement` returns early for it, skipping the reset the other cases do) — the Sell button toggles it off explicitly instead, so selling several rooms doesn't mean re-pressing Sell before every single one.
- Mining reuses `ApplyDigDamage`/`ApplyHit`'s existing return-a-bool-for-"destroyed" shape by just widening it with `out` params (`resourceType`, `resourceAmount`) rather than a parallel resource-specific method — a plain wall always reports `ResourceType.None`/`0`, so `TickDigging` can keep discarding them (`out _, out _`) without needing to know resource walls exist at all.
- No combat yet, and only a first pass at economy (gold + mana, no spending) — intentionally out of scope for Phase 1 per the brief, the resource/inventory/deposit system was added on top afterward.
- `ImplingAgent.PlanPathTo` used to ignore `AStarPathfinder.TryFindPath`'s return value — on failure it left `_waypoints` with just the single destination point, so `MoveAlongPathThen`'s plain `Vector3.MoveTowards` would walk straight at it in a line, clipping through whatever blocked the route (a wall built across the way home, most visibly). Job travel never hit this in practice since `BuilderJobBoard` pre-verifies reachability before assigning a job, but returning to the Lair and traveling to a deposit target (Treasury, Chaos Core) had no such guarantee. Fixed by having `PlanPathTo` return whether a path was actually found; every caller now only transitions into a moving state on success, and just stands pat otherwise — `TrySeekJob` re-runs every frame regardless of state, so a blocked impling automatically retries and resumes on its own once the world reconnects, no separate retry timer needed.
- Making Treasury a real, player-buildable room (rather than only a fixed starting landmark) meant reusing Lair placement's shape without reusing its code: `TreasuryManager.TryPlaceTreasury`/`UpdatePlacementPreview`/`ClearPlacementPreview` are each `LairManager`'s equivalent copy-adjusted for Treasury's own visual (border/fill tiles + gold label instead of the unclaimed/claimed nest visuals), following the same "own copy per room type" precedent the job-kind system already established, rather than forcing both room types through one shared placement class. What *did* get extracted into a shared spot, because it was genuinely the same rule with zero room-type-specific behavior, was the footprint validity check itself — `DungeonGrid.CanBuildRoomOn` — so `LairManager.CanPlaceFootprint` and `TreasuryManager.CanPlaceFootprint` both just loop calling it instead of each re-deriving "Claimed, dug, room-free, buildable Floor." The harder part was selling: rather than teaching `LairManager.TrySellRoom` about Treasury-specific bookkeeping (or duplicating a second Sell tool), `TreasuryManager` subscribes to the `RoomSold` event `LairManager` already fired (previously documented as "nothing currently listens") and reacts only to roomIds with its own `"Treasury_"` prefix — so the existing generic Sell tool works on Treasury rooms with zero changes to `TileInteractionController` or `LairManager` themselves. GameBootstrap's starting Treasury moved from a direct `RegisterTile` loop to `TryPlaceTreasury` for the same reason implings starting on the Chaos Core platform go through the real spawn path rather than a special-cased shortcut: a "fixed" room should still be an ordinary instance of the mechanic, not a parallel code path that has to be kept in sync with it by hand.
- Every room tile now carries an HP of 50 (`TileState.RoomMaxHp`), set the moment `DungeonGrid.TryAssignRoom` assigns a `RoomId` — that single funnel point means it applies to every room kind (Lair, Treasury, Bacon Beacon, Training Room, Slime Hatchery, Library) with no per-manager changes. Nothing damages it and no UI shows it yet; it's tracked data only, ahead of a future room-durability mechanic.
- Auto-reinforce (Impling menu, default off) lets `BuilderJobBoard` queue reinforce jobs itself instead of requiring a manual tap per wall. Enabling it just flips `_isAutoReinforceEnabled`, which makes `Update()` run `ScanForAutoReinforceCandidates` once a second: it walks the whole grid and calls the same `DungeonGrid.RequestReinforce` a manual tap would on every Rock tile bordering already-Claimed floor (the same "dungeon wall" candidacy `TryClaimClaimJob` already uses for claim jobs) — `RequestReinforce` itself no-ops on anything ineligible or already queued, so re-scanning a mostly-settled dungeon every second is cheap and idempotent. Once queued, an auto-generated reinforce job is indistinguishable from a manually-tapped one — it goes through the exact same pending-grace-period-then-open flow and the exact same `TryClaimReinforceJob` assignment, so implings pick it up with zero new state on the agent side.
